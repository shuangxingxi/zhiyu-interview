# 评分参照库（Scoring Rubric Library）实施计划

> 目标：给评估官一份「分层考点 → 要点清单 / 常见误区」的参照，让评分有据可查，降低大模型幻觉评分。
> 定位：这是**内部质量提升**，不改变演示观感。
>
> ⚠️ **历史文档说明（2026-10-15 补注）**：本文是 v2.1 的**原始实施方案**，
> 保留以记录当时的决策过程。文中部分数字已随 v2.2 扩容而过期，阅读时请注意：
> - 文中「90 条考点参照」实为 **270 条**（v2.2 起每档由 5 条扩容到 15 条：
>   6 专业 × 3 难度档 × 15 条 = 270）；
> - `rubrics.json` 与 270 考点仍保持**一对一**，未破坏 1:1 对齐；
> - v11 另修了一个本文未预见的问题：评估官曾拿到该难度档**全部** 15~17 条参照，
>   把没问到的考点判成考生遗漏；现改为只注入 `asked_topics` 命中的条目。
>
> 当前权威描述见 `DESIGN.md` 第七、八节。

---

## 一、问题

现在评估官判断「答得对不对」完全依赖模型自身知识。`EVALUATOR_SYSTEM` 里只给了：

- 评分维度（来自 `profile["dimensions"]`）
- 提问深度、严格度（来自难度档）
- 一整段面试记录

**没有任何「这道题应该答到什么」的对照物。** 后果：

1. 同一份回答，两次评分可能不一致（无锚点）
2. 模型凭印象判分，可能把正确答法判成错误（幻觉扣分）
3. 教练说「这里讲得不够深」，但说不出「具体漏了哪个要点」，建议空泛

现有 `knowledge.py` 的 `topics` 只是**题目方向**，不是答案要点。例如
`"进程与线程的区别及各自开销"` —— 只有题，没有「答到哪几条算扎实」。

---

## 二、核心设计决策

### 2.1 用「要点清单」，不用「标准答案」

这是本方案最关键的取舍。

面试是开放作答，候选人的表述千变万化。如果给评估官一段"标准答案"，会诱导它做**字面比对**：
候选人讲对了但用词不同 → 判错。这比没有参照**更糟**。

所以每条 rubric 写成三元组：

| 字段 | 含义 | 判分用途 |
|---|---|---|
| `must_hit` | 必须命中的核心要点（2–4 条） | 少一条扣一档 |
| `bonus` | 加分项（能体现深度的延伸） | 命中加分，不命中不扣 |
| `common_errors` | 常见误区（概念性错误） | 踩中直接扣，且要写进 risks |

### 2.2 rubric 是「参照」不是「天花板」

提示词必须显式声明：**候选人给出 `must_hit` / `bonus` 之外但同样正确的答法，必须照常给分。**
否则 rubric 会变成上限，反而压低分数。这条不加，特性就是负资产。

### 2.3 数据与代码分离

90 条 rubric 是散文式内容，塞进 `knowledge.py` 会把代码撑爆，也不便人工校订。
所以落成 `rubrics.json`（标准库 `json`，不新增依赖），加载器放在 `knowledge.py`（它本来就是"库"模块）。

## 三、数据结构

`rubrics.json`：

```json
{
  "计算机科学与技术": {
    "进程与线程的区别及各自开销": {
      "level": "B",
      "must_hit": [
        "进程是资源分配的基本单位，线程是 CPU 调度的基本单位",
        "同一进程内的线程共享地址空间，进程之间相互隔离",
        "线程切换不涉及页表/地址空间切换，开销小于进程切换"
      ],
      "bonus": ["能按场景选型（IO 密集用多线程、CPU 密集用多进程）", "提到协程或用户态线程"],
      "common_errors": ["说成「线程是资源分配的基本单位」", "认为同一进程的线程各自独立内存"]
    }
  }
}
```

- 键 = `专业 → 考点原文`（考点字符串直接取自 `MAJOR_MODEL[major]["topics"][level]`，保证与出题完全对齐）
- `level` 只作元信息。检索按 `(专业, 考点)` 命中，**不按难度过滤**——因为 A 档会把 B 档的 2 条考点一并带入（见 `build_profile`），按难度过滤会漏。

规模：6 专业 × 3 档 × 5 条 = **90 条**。行为面不单独做（6 道题是通用 STAR 题，已有 `_STAR_EXTRA` 覆盖），走通用标准。

## 四、接入方式

### 4.1 `knowledge.py` 新增

```python
RUBRIC_FILE = Path(__file__).with_name("rubrics.json")

def load_rubrics() -> dict: ...      # 文件缺失/损坏 → 返回 {}，绝不抛异常
def rubric_for(profile) -> list:     # 按 profile["topics"] 取出本场命中的条目
def rubric_block(profile) -> str     # 拼成注入提示词的段落；无命中时返回降级文案
```

### 4.2 `agents.py` 修改

`EVALUATOR_SYSTEM` 新增段落：

```
【考点评分参照】本场面试官问到了下面这些考点，请对照要点清单判分。
{rubric_block}

参照使用规则：
1. must_hit 是核心要点，候选人没讲到就要扣，并写明漏了哪条。
2. 候选人给出参照之外的正确答案，同样要算分——参照是底线不是天花板，禁止因为「和参照不一样」而扣分。
3. common_errors 里踩中的概念错误，必须写进 risks。
4. 本场题目若不在此参照范围内，标注「无参照」，按通用标准正常评。
```

JSON 新增**可选**字段：

```json
"rubric_check": [
  {"topic": "考点", "must_hit": ["命中的要点"], "missed": ["遗漏的要点"],
   "errors": ["踩中的误区"], "comment": "一句话说明"}
]
```

设为可选的原因：模型漏输出时不能让整份报告崩。解析后做 `.get` 兜底，报告页无该字段则不展示。

### 4.3 `app.py` 修改（报告页）

tab1 增加一个 expander「考点命中情况」：
- 有 `rubric_check` → 表格展示（考点 / 命中 / 遗漏 / 误区）
- 没有 → 不渲染（不报错、不留空壳）

### 4.4 教练

`coach_review` 的 user 消息带上 `rubric_check` 的遗漏要点，让 `drills` 落到"补哪个要点"而不是"多练习"。

## 五、降级与容错（必须全部成立）

| 场景 | 行为 |
|---|---|
| `rubrics.json` 不存在 | 加载器返回 `{}`，`rubric_block` 返回「本场未提供考点参照」，评估照常 |
| 本场考点不在库内（如新增专业） | 同上，按通用标准评 |
| 模型不输出 `rubric_check` | 报告页跳过该区块 |
| 模型输出格式错但主字段正常 | 沿用现有 `_loads_lenient` 容错 |
| rubric 内容本身有误 | 见 §七 质量门——**必须抽检后才能上线** |

**红线：任何情况下评分功能不能因为参照库缺失或损坏而中断。**

## 七、质量门（本方案最大的风险点）

风险：rubric 写错 → 错误的知识点成为**评分依据** → 比没有参照更糟。

所以：

1. **不手工写 90 条**（工作量不现实）。用 DeepSeek 从现有考点批量生成，每批 5 条，共 18 次调用。
2. 生成脚本放临时目录，产出直接写 `rubrics.json`。
3. **必须抽检**：6 个专业各抽查 2 档 × 2 条 = 24 条，重点看 `must_hit` 是否准确、`common_errors` 是否真属于常见误区（不是编的）。
4. 抽检不通过 → 修正后重跑该专业，不带病上线。

## 八、实施顺序（三阶段）

**阶段一 · 打通链路（一个专业）**
1. 定义 JSON 结构与加载器，写好降级分支
2. 手工写「计算机科学与技术」B 档 5 条作为样例，跑通注入与展示
3. 补覆盖度单测 + AppTest 回归

**阶段二 · 补齐数据**
4. 批量生成其余专业/难度，写入 `rubrics.json`
5. 覆盖度断言：6 专业 × 3 档全部考点都能命中
6. 人工抽检 24 条，修正

**阶段三 · 在线验证与文档**
7. 跑一场真实面试，对比接入前后评估官评语的具体程度
8. 确认 `rubric_check` 正常产出、遗漏要点进入教练 `drills`
9. 同步 `DESIGN.md` 并导出 `DESIGN.docx`

## 九、验证方案

| 项 | 方法 | 通过标准 |
|---|---|---|
| 加载与降级 | 单测：文件缺失 / 损坏 / 正常 | 三种情况都不抛异常 |
| 覆盖度 | 断言全部 90 条考点可命中 | 命中率 100% |
| A 档跨界考点 | A 档 profile 的 topics 含 B 档 2 条，断言也能命中 | 通过 |
| 提示词装配 | `EVALUATOR_SYSTEM.format(...)` 无缺参 | 通过 |
| 界面回归 | AppTest：有/无 `rubric_check` 两种报告 | 均不报错 |
| 在线对比 | 同一份回答，接入前后评估官评语 | 评语能指出具体遗漏要点 |

## 十、已知风险

| 风险 | 应对 |
|---|---|
| rubric 内容错误成为评分依据 | §七 质量门：生成 + 24 条人工抽检后才上线 |
| 参照变成分数天花板 | 提示词显式写明「参照是底线不是天花板」，并列入验证项 |
| 提示词变长稀释指令 | 每场只注入本场 5–7 条，不是全量 90 条 |
| 新增字段导致 JSON 解析崩 | `rubric_check` 设为可选，全链路 `.get` 兜底 |
| 占用时间挤压大赛材料 | 阶段一完成即可评估收益，不满意可停在阶段一 |

## 十一、与比赛的关系

材料里的口径要写对。**不要**把它包装成 RAG：

- 现状：字典查表（结构化配置），替代向量库
- 新增：结构化 rubric 参照，替代「凭印象判分」
- 两者的共同理由：本场景数据量小、字段可精确命中，向量检索是纯复杂度开销

这条技术取舍本身就是评委想看的判断力。用错口径（硬套 RAG）反而会被追问。
